current rewritten repository, use the [commit map](matlab_data_lfs_commit_map.csv).
MATLAB `data/` contents are preserved through Git LFS with hashes in the
[manifest](matlab_data_lfs_manifest.tsv).

Inspected 2026-09-23. Paths are relative to `migration_work/ACE_MATLAB/`. Collection identifiers and byte identities are defined in [inventory](matlab_inventory.md); evidence and change classifications are in [lineage](matlab_lineage.md). Versions are artifact identifiers, not assertions of release order.

“Source package” means a main plus accompanying libraries. It does not certify execution, correct physics, or complete input data. High confidence applies to observed contents and Git identities; medium confidence to inferred development relationships; low confidence to unresolved historical provenance. Developer-defined baseline assignments are decisions, not historical confidence ratings; they do not alter lineage confidence.

## Developer-defined migration convention

For historical standalone MATLAB mains without their own utility directories, the assigned baseline is **v0.18-era root utilities by developer-defined migration convention.** This applies to `ace_v019_K24_8aces.m`, `ace_v019_dev_2d88aces.m`, and `ace_v020_dev_2d88aces.m`. The baseline is collection R: the 100 root utility files whose Git identity is recorded in the inventory. Snapshots with their own utilities retain their documented accompanying collections.

The evidence categories are distinct:

- **Git-confirmed historical facts:** the root utility bytes and their introduction in the MATLAB Git history.
- **Source-code inference:** driver-family relationships and compatibility findings derived from source comparisons.
- **Developer-defined migration decision:** assigning R to standalone mains for migration. This resolves the baseline selection; it does not establish which utilities, working directory or MATLAB path were used historically, prove numerical compatibility, or change the inferred source lineage.

## Utility compatibility conclusions

The root utility tree is exactly the Git v0.18-era tree: 96 utility files were introduced in `8e5cb2d`, and four were added in `fda0904`, for 100 files including nested backups/tests. None was subsequently modified in the inspected MATLAB Git history.

Standalone mains add library paths relative to `pwd`, not their own file location. Consequently, executing a root main while working inside a snapshot could select that snapshot's utilities. The archive does not record which working directory or MATLAB path was used historically. For migration, the developer assigns v0.18-era root utilities to standalone mains without their own utility directories. The actual historical execution environment remains unverified.

The older mains' two-argument `eval_Tv`/`eval_qsat`/`eval_q` calls cannot generally be paired unchanged with S20/S24 implementations, whose optional branches were disabled and whose drivers instead use explicit condensate arguments or `*2` functions. Matching filenames alone would miss this incompatibility. S19's k=6 default specifically makes the later vector-WENO corrections relevant; the k=2 standalone defaults do not establish the correctness of higher-order branches.
